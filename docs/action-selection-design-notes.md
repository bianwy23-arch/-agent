# 追问、查看证据、继续搜索与停止：设计备忘

状态：五项基础原则与七项补充原则均已由用户确认并要求记录；尚未实现。

补充确认日期：2026-09-08。

本文延续 [Decision State 设计备忘](decision-state-design-notes.md)。这里记录本项目的设计选择，不将其表述为参考文章作者的实现。

## 核心判断

围绕“当前还缺什么决策依据”选择动作，不以字段填满、固定搜索次数或固定候选数量为目标。

| 当前缺口 | 优先动作 |
| --- | --- |
| 只有用户知道且会影响决策的信息 | 追问 |
| 已有候选的相关事实还没有查看 | 查看商品证据 |
| 已有候选不足以支撑当前决策，且还有有效检索方向 | 继续搜索 |
| 已能回答当前问题，或当前能力无法取得进一步有效信息 | 停止本轮工具调用，交付与证据相称的结果 |

查看已有候选证据是独立动作，不能全部混入“继续搜索”。追问、搜索与查看证据的先后由具体缺口决定，不要求每次固定先追问或先搜索。

## 已确认原则

### 1. 追问应实质影响下一步决策

值得追问的问题至少满足：

- 答案主要掌握在用户手里。
- 不同答案会改变候选资格、重要排序，或当前任务的执行方式。
- 已有上下文与工具无法可靠获得答案。

预算、品牌、颜色尚未填写，不自动构成追问理由。结合回答成本，用用户能理解的使用场景提问，不要求用户先掌握专业参数。

例如“宿舍用的电热水壶”可以先检索；如果明确要求“宿舍限功率，不能跳闸”，未知的允许功率上限直接影响资格，应询问，不能从商品资料推断宿舍规定。

有值得问的问题不等于全部工作暂停。可以先执行不依赖答案的动作，或提供条件性比较；真正影响正确执行的歧义只阻塞相应部分。这与明确、独立的需求修改立即生效的规则一致。

用户已明确无偏好的维度，不重复追问；已知答案优先读取当前任务状态。

### 2. 继续搜索应弥补具体缺口

每次追加检索须能说明：当前缺什么、本次改变什么、预期获得什么新信息。

合理原因包括：现有候选均超预算、用户排除当前品牌、需要补充轻量候选、用途变化导致原候选不再适合。不得为产生结果而暗中放宽硬约束。

已有 A、B 却未查看规格，应查看证据；事实清楚但取舍优先级未知，应追问或给条件性建议，不靠增加更多商品回避取舍。

进展不限于新商品 ID：补齐决定性事实、排除错误候选、在完整检查的明确范围内确认无匹配，也属于进展。反复返回相同商品和证据不算进展。

### 3. 停止本轮执行不等于用户已经选定

回答充分性取决于当前请求：问“A、B 哪个更轻”，核实并回答重量即可，不必完成整个购买决策；请求推荐时，需有满足明确硬约束的候选、支撑关键理由的证据，并能解释重要取舍。

不要求所有软偏好都明确，也不要求凑够三个候选。未知的关键硬约束证据不能按“已满足”处理，条件性讨论或部分匹配须明确标识。

Agent 给出推荐不自动将 Decision State.selection 标记为用户已确认。只有用户明确选择，才能记录已选定；已选定仍不代表购买执行。

| 停止原因 | 交付 |
| --- | --- |
| 当前问题已回答 | 答案或比较结论 |
| 已具备推荐依据 | 推荐、理由和重要取舍 |
| 需要用户决定 | 关键问题或清楚的选择分支 |
| 当前商品库没有匹配项 | 说明检查范围和不满足的条件 |
| 数据缺失或执行受限 | 说明已确认内容和仍无法确认的内容 |

无匹配、数据不足、执行上限触发不能记录为推荐成功。等待用户回答是本轮暂停，任务仍可继续；停止原因与 Shopping Task 的购买决策状态分别表达，具体字段待实现时确定。

### 4. 利用有限商品库提供确定的检查范围

第一版每类 50 条商品。品类、币种和明确价格上限等可计算条件，由程序遍历当前品类并返回准确结果，不依赖模型反复改写查询来猜测。

必须区分：

- 已完整检查当前商品库中的明确条件。
- 某次语义检索没有召回。
- 有相关商品，但判断所需证据缺失。

只有第一种能支持相应有限范围内的无匹配结论。不能将“当前目录内没有”扩展成市场上没有，也不能将“没有长时间佩戴舒适度证据”解释成商品不舒适。

非结构化、含糊或依赖场景的条件不因为商品数少就自动成为可确定计算的条件。历史 USD 价格维持其真实币种与时间口径。

### 5. 调用上限作为执行后备措施

主要逻辑是：判断当前回答是否充分 → 定位关键缺口 → 选择能解决缺口的动作 → 根据反馈更新判断。

不把“问两次、搜三次”作为统一业务结束标准。工具上限、耗时/成本预算和重复无进展检测用于防止失控；触发时说明结果不完整，不伪装成成功。

模型提出当前缺口与动作理由；程序检查可确定的底线，例如不擅自放宽硬约束、不将无证据的事实认定为已确认、不将给出推荐等同于用户选择。不以模型自报置信度代替这些检查。

## 已确认补充原则

### A. 用户不回答、答不出来，或要求直接推荐

“随便，你推荐”应允许给出有依据的默认方案或分支建议，不意味着可以放宽已经明确的预算等硬约束。不把用户没回答当成明确无偏好；“不知道”与“不在意”分别处理。

对同一未解决问题重复换说法通常没有价值。优先说明影响、使用更容易理解的选项，或给条件性结果。若缺失信息使硬条件无法核实，明确这个限制，不制造确定结论。

### B. 只优先补查可能改变决定的未知事实

不要求检查所有候选的全部字段。已经明确超出硬预算的商品，其续航未知通常不值得优先补查；当前最有希望的候选能否满足关键条件，则应优先查看。

判断依据是明确淘汰条件、用户当前关注对象及可能改变结论的差异，不能用未经验证的粗排分数排除潜在合适商品。若没有合格候选且仍有潜在可行项，不能提前宣布无匹配。

### C. 无匹配后先诊断需要放宽哪项，再交给用户取舍

对可准确计算的条件，可以在不修改正式需求的前提下进行反事实筛选，例如“只移除颜色要求”和“只提高预算”的结果有什么区别。把具体选择反馈给用户，避免笼统地追问是否提高预算。

这种探索属于临时分析，不改变正式 Requirement State。不将未知事实当成放宽一项后必然满足的证据，也不将有限范围内的分析称为全局最小让步方案。

### D. 用户对本轮范围和停止的明确指令优先

“先别找新的，只比较这两个”应约束本轮搜索范围；可以查看这两个已有商品的证据。用户说“先到这里”，应停止继续探索，不因内部认为还可优化而继续调用工具。

“直接推荐”可以结束非必要追问，但不免除证据要求。这类指令首先作用于当前交互，不自动变成长期商品偏好。

### E. 多个问题都值得问时，优先选择最能推动当前决策的问题

不要因多个问题都有用就一次全部追问。优先考虑能避免明确选错的问题、会改变当前主要候选或推荐方向的问题，以及用户容易回答的问题；根据具体任务权衡，不预先设定未经验证的数值评分或固定问卷。

例如通勤耳机，可先询问能否接受入耳式或头戴式，而不是同时追问品牌、颜色、编码协议和精确续航小时数。

候选集合被平均分开，不等于问题有价值。即使颜色能把候选分成两半，用户不在意颜色时，也不应仅为了缩小搜索范围而追问。问题价值取决于用户的决策，而非单纯的信息量或候选数量变化。

### F. 检查整个决策过程是否原地打转

不只检查工具名称和参数是否重复，还要检查是否在没有新依据的情况下重新尝试同一个已失败或被用户拒绝的方向。

例如“问预算 → 搜索 → 建议加预算 → 用户拒绝 → 换关键词搜索 → 再建议加预算”，即使单次调用不同，整体仍没有进展。

记录已询问的问题、用户回应、已失败或被拒绝的探索方向，以及重新尝试所需的新条件。用户明确拒绝提高预算后，关闭当前任务中的这条放宽路径，不重复劝说。用户主动改变预算可重新打开该路径；新的相关商品证据可以支持在原预算内重搜，但不能被当作用户允许加预算。换一种措辞不算新条件。

失败路径不是永久黑名单；是否重试由当前需求和实质的新信息决定，不沿用已失效的失败结论。

### G. 结论强度与证据、比较范围匹配

“可以推荐一个合适商品”和“有依据说它最好”是不同的完成标准。

| 结论 | 所需依据 |
| --- | --- |
| A 满足明确要求 | A 的相关证据充分，明确硬约束已核实 |
| A 比 B 更符合某项偏好 | A、B 在对应维度上的证据可比较，且偏好有依据 |
| A 是当前商品库中最便宜的合格商品 | 已完整检查相应范围，潜在更便宜商品的资格不存在未解决的证据缺口 |
| A 是市场上最好的 | 当前有限商品库不能支持这种结论 |

用户只要求“找个合适的”，不必穷尽所有比较；用户明确要求“找最便宜的”，不能找到第一个合格商品就视为完成。更便宜的候选若仍有资格证据缺口，应继续核验，或将结论限定为“已核实候选中最便宜”，同时明确原请求尚未完全解决，不能静默降低目标。

不因一次局部检索或粗排得分，就把“符合要求”升级为“最适合”“最便宜”或市场级最优结论。

## 后续验收方向

已确认原则的基础场景：

- 字段尚有空缺，但当前比较问题已有充分证据：回答并停止，不补问无关字段。
- 信息只能由用户提供，且影响硬约束：追问相应缺口，独立动作可继续。
- 商品已找到但决定性规格未读：查看证据，不重复搜索。
- 取舍依赖用户偏好：提出场景问题或条件性建议，不无限增加候选。
- 完整价格过滤无结果、语义检索无召回、证据缺失分别产生不同反馈。
- 用户未放宽条件：检索失败后正式需求不变。
- 新事实改变资格但未新增商品 ID：仍识别为有效进展。
- 已有一个证据充分的合适候选：允许推荐，不强制凑三个。
- 调用上限触发：结果记录为受限，而不是推荐成功。
- Agent 推荐 A 后用户尚未表态：selection 不变成已确认。

七项补充原则的验收场景：

- 用户回答“不知道”“不在意”“你推荐吧”：分别处理，不混成同一种状态；默认方案不突破明确硬约束。
- A 已明确超预算、B 的关键规格未知：优先补查 B，不要求所有候选所有字段都完整，也不漏掉潜在可行候选。
- 无匹配时分析不同放宽方向：呈现具体取舍，正式需求保持不变，缺失证据不变成满足证据。
- 用户要求只比较 A、B：不新增候选，可补查 A、B；用户要求停止时不继续探索。
- 多个问题同时可问：优先考虑决策影响与回答成本，不为了均分候选而询问用户不关心的颜色。
- 用户拒绝加预算：换关键词或换问法后不再次劝加预算；用户后来主动修改预算时可重新评估。
- 工具调用形式不同但状态与证据无变化：仍能识别为整体无进展。
- “找个合适的”与“找最便宜的”：采用不同的完成标准；更便宜候选资格未知时不直接宣称当前商品库最低价。
- 有限比较结论明确限定范围，不扩展成市场最优结论。

工具晚回覆盖状态的并发问题继续按此前约定暂缓；本备忘没有重新引入该要求。
