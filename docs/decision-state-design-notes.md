# Decision State 设计备忘

记录日期：2026-09-06。

补充日期：2026-09-07，明确澄清期间的生效规则、撤销范围与非法更新处理。

状态：用户认可并要求保留的设计方向，供后续重构讨论使用；尚未实现，不代表当前运行行为。新设计可以重新划分现有项目边界。

## 任务与状态的关系

Shopping Task 表示一次持续的购物任务。Requirement State、Candidate State 和 Decision State 是其中职责不同的组成部分，可以嵌入同一任务对象，无须因此拆服务或数据库表。

- Requirement State：当前有效的需求，如预算、用途、硬约束、软偏好及优先级。
- Candidate State：商品事实、候选资格、淘汰原因和待核验信息。
- Decision State：用户正在讨论哪些商品、纠结什么、保留或否定了什么、是否已作出选择。

同一事实只维护一个权威值。预算属于需求状态，商品重量属于候选事实，不在决策状态重复维护。

## 最小决策状态

| 字段 | 含义 |
| --- | --- |
| phase | 探索、比较、待确认、已选定 |
| focus_ids | 当前正在讨论的商品 |
| shortlist_ids | 用户明确保留的商品，不等于全部检索结果 |
| unresolved_tradeoffs | 尚未解决的取舍与决策问题 |
| selection | 暂时倾向或明确选定的商品，必须区分两者 |

另保存简短的决策事件历史，记录动作、商品、用户原话、原因和轮次。当前状态用于执行，历史用于解释与撤销；这并不预先要求采用完整事件溯源架构。

## 更新机制

模型读取当前状态和用户表达，提出结构化变化；程序检查商品标识、指代和用户表达依据后应用。避免让模型直接重写整个 Shopping Task。

例如“这两个哪个更适合每天背着去学校？”可以产生比较动作、两个目标商品、待解决问题以及对应用户原话。

| 用户表达 | 状态变化与动作 |
| --- | --- |
| 比较 A 和 B | 更新讨论对象，进入比较阶段，获取关键差异 |
| A 不考虑了 | 记录排除决定，移出讨论范围；不推断整个品牌被排除 |
| 这两个都太重了 | 判断便携要求是否变化，更新需求后重排，必要时重新搜索 |
| A 的续航到底怎么样 | 记录决策问题，补查事实 |
| 我比较倾向 A | 记录暂时倾向，保留未解决问题 |
| 还是把 A 加回来看看 | 撤销用户对 A 的排除，按当前需求重新检查资格 |
| 就选 A | 记录明确选择，继续核对必要规格与事实 |

用户明确选定商品不代表 SKU、价格等必要事实已经确认，也不代表购买已经执行。

## 需求更新与结论有效性

为 Requirement State 维护版本号，比较结论绑定所依据的需求版本。版本变化触发有效性检查；受变更影响的旧结论需要重新评估，不代表所有事实和结论全部清空。用户明确保留、排除的决定继续保留，除非撤销；其当前候选资格仍需重新检查。

需求更新须区分新增、修改、撤销与冲突：

- “不要游戏本”：新增排除要求，保留其他需求。
- “预算提高到 8000”：明确替换预算。
- “重量无所谓了”：撤销重量要求，不推断偏好重电脑。
- “如果加到 8000，会有什么区别”：条件性分析，保留正式预算。
- “绝不超过 6000”之后询问 7500 的商品：不自动放宽预算，必要时澄清。

当前表达优先的前提是理解其作用；疑问、假设与明确修改不能等同。模型根据场景推断的偏好不能自动升级为硬约束。

## 状态更新的实现思路

以下方向已获用户认可。优先保证不误改；明确修改直接执行，仅对会影响执行的真实歧义作必要澄清。

### 1. 区分正式需求、临时探索和候选例外

每轮先判断用户表达的作用，再提出更新：正式修改、假设探索、候选例外或普通询问。

- “预算改成 8000”：修改正式需求。
- “8000 能买到什么”：在临时方案中探索，不改正式预算。
- “这台 7500 的也留着看看”：保留该候选，不把全局预算放宽到 7500。
- “还是按原来的来”：在指代明确时退出临时方案，恢复原讨论范围。

第一版最多维护一个临时探索方案，保存与正式需求的差异及原讨论范围，不引入复杂分支树。用户正式接受其中条件后，再通过正常更新流程写入正式需求。

shortlist_ids 允许保留不满足当前硬约束的商品，但必须明确标记违反的条件。用户愿意继续比较，不等于它获得了合规主推荐资格。

### 2. 整体解析一轮变化，按依赖关系分组应用

模型提出本轮完整的更新集合，程序先检查目标、依据、条件关系与相互一致性，再按依赖关系分组。明确且独立的变化直接应用；有歧义的变化暂缓，保留对应原状态并澄清；相互依赖的变化成组校验和应用，不能拆开生效。

例如“A 删掉，预算提高一点”，可以立即排除 A，保留原预算并询问新的预算范围；“如果放宽预算，就把 A 加回来”，恢复 A 依赖预算条件，不能单独执行。此规则取代此前“一轮存在歧义就保留全部原状态”的设想。

例如“A 不考虑了，预算还是 6000，但重量低于 1.2kg 可以加到 7000”，解析必须覆盖排除 A、通常预算和条件性预算例外；预算例外与重量条件成组处理，不能只抽出 7000 覆盖预算。

更新提议至少需要表达：操作类型、作用范围、目标字段或商品、值与单位、适用条件、信息来源、对应用户原话。具体协议尚待确定。

需求表示需要保留语义差异：明确上限（最多 6000）、近似目标（6000 左右）、排序偏好（越轻越好）和条件关系（低于 1.2kg 才考虑加预算）。不能自行给近似目标指定浮动范围。第一版不要求支持任意复杂条件；无法可靠表达时澄清，不静默丢弃条件。

### 3. 区分修正、需求冲突与表达歧义

| 情况 | 处理原则 |
| --- | --- |
| 明确修正，如“之前说错了，是给我爸买” | 更新相应需求，检查相关推断，不删除无关条件 |
| 多个要求难以同时满足 | 保留需求，通过搜索判断是否可满足，再说明取舍；不擅自放宽 |
| 新表达可能是修改，也可能是例外 | 保留原需求，必要时确认作用范围 |

需求来源至少区分用户明确表达、系统推断与默认设置，并保留轮次及原话依据。来源和作用语义优先于模型自报的数值置信度；高置信度推断不得覆盖用户明确要求。

搜不到商品不等于需求状态有错。系统不能为了产生推荐而自动提高预算、降低配置或取消排除条件。

### 4. 按影响范围检查事实、资格与结论

需求变更产生受影响字段集合，据此检查候选资格、排序和推荐解释。

- 商品重量等事实通常仍可保留；价格等信息另外按时效判断。
- 便携优先改为性能优先，会影响排序和取舍结论。
- 用户明确表达的外观厌恶等独立决定继续有效。
- 系统依据旧预算过滤的商品，在预算提高后可以恢复资格。
- 用户明确拒绝的商品，不因需求变化或重排自动回归。

区分系统过滤原因与用户排除决定，分别记录各自依据。明确恢复商品时，撤销用户排除，但仍重新检查其当前资格。

### 5. 把指代绑定到实际展示结果

为每批展示结果保存展示标识、商品顺序和任务关联，使“第二个”“前两个”等引用落到用户实际看见的商品，而不是最新的后台排序。

在条件允许时，由界面随反馈提供展示标识或明确商品标识；文本指代解析同时参考展示记录与当前讨论对象。多批展示导致无法确定时，简短澄清。

一句话含多个指代时，先统一解析，再应用变化。例如“第二个不要，前两个比较一下”，不能先删除第二个，再把位置移动后的商品当作“前两个”；如果排除与比较意图的先后含糊，保留原目标并澄清。

### 6. 判断任务归属与跨任务继承

先判断用户在继续当前 Shopping Task，还是开始另一项购物任务。第一版可保留多个任务，但一次只操作一个当前任务，无须引入复杂多任务规划。

- 从“通勤耳机，500 以内”转到“再给我爸找个手机”：创建新任务，不自动继承耳机预算、通勤场景或品牌排除。
- “耳机先不买了，这 500 块拿来买个音箱”：新任务可以继承用户明确指出的预算，其他需求不自动迁移。
- “再看看苹果的”：结合当前品类判断是否仅为品牌调整；只有任务归属确实含糊时才澄清。

跨任务继承仅采用用户明确表达的条件，保留来源引用。这里处理的是用户输入的任务归属，不包含暂缓的异步工具结果回传问题。

### 7. 区分未知、明确无偏好与已撤销要求

当前需求状态区分未知、明确无偏好与有效要求；撤销作为历史事件保存，不强求与前三者做成同层字段。

| 语义 | 示例 | 后续行为 |
| --- | --- | --- |
| 未知 | 用户尚未表达重量要求 | 影响选择时可以询问 |
| 明确无偏好 | 重量无所谓 | 不继续追问，不自动恢复重量偏好 |
| 有效要求 | 最好轻一点 | 按软偏好参与排序 |
| 撤销事件 | 刚才那个轻薄要求取消 | 原要求失效，保留撤销依据 |

撤销后不能仅凭旧对话中的“每天通勤”立即恢复便携优先。保留用户修正的作用范围与轮次，避免旧推断重新生效；后续新的明确要求仍可以更新该字段。撤销具体要求不一律等于该维度永久无偏好，应依据用户实际表达确定当前语义。

### 8. 需求撤销后检查衍生推断

每条系统推断除了记录来源类型，还要引用它依赖的用户表达或需求。依据发生变化时重新检查相关推断，有独立有效依据的要求继续保留。第一版使用简单来源引用，不建设通用依赖图系统。

例如“每天背电脑去学校”可推断便携和续航偏好；用户改为“就放宿舍，不用带出门”，这些推断需重新评估。若用户还明确说过“我就是喜欢轻的电脑”，便携偏好仍有独立依据，不应一并删除。

### 9. 澄清期间，明确且独立的修改立即生效

“A 排除，预算提高一点”：立即排除 A，预算保持原值，只等待新的预算答案。用户取消预算澄清，不回滚已生效的排除 A；取消待澄清请求与撤销已生效修改是不同动作。

待澄清部分记录目标字段和原话依据，明确区分本轮已应用、待澄清和未应用的变化。相互依赖的变化仍按第 2 节成组处理，不因这条规则提前执行。

### 10. 撤销按用户指定范围执行

用户未指定局部范围而说“撤销刚才的修改”，默认撤销上一轮已经生效的用户修改组；若上一轮包含多个独立且已生效的组，撤销这些组。尚未生效的提议不算作可撤销的已应用修改，不能误撤更早轮次。

用户说“只恢复预算”，表示只撤销对预算的修改，恢复对应的修改前预算，其他独立修改继续有效。这不表示删除预算约束或清空预算。

例如原预算为 6000 元，用户说“预算提高到 8000，A 不考虑了”，之后说“预算还是按原来的来，A 依然不要”：预算恢复为 6000 元，A 仍被排除。若改说“撤销刚才的修改”，则撤销该轮预算提高和排除 A 的决定；恢复 A 后仍按当前有效需求检查资格。

实现时，历史记录保留轮次、修改组标识、作用目标及修改前后值，支持按组或字段定位撤销。范围有真实歧义时才澄清；存在条件依赖时检查依赖关系，不能局部恢复出自相矛盾的条件。

撤销作为新的状态变化记录。随后重新检查衍生推断、候选资格、排序和结论，不直接恢复整个历史快照，避免覆盖无关修改或后来取得的商品事实。

### 11. 非法结构化更新不写入状态

程序校验更新提议的格式、目标、值、条件与组内一致性，拒绝不合法的对应更新组并保留原值。合法、明确且独立的其他组仍按第 2 节应用。若整个输出无法解析，无法可靠识别组边界，则不应用该输出。

模型输出格式或协议错误允许内部有限重试，重试次数在实现时配置；程序提供具体校验错误供模型修正，修正后仍需通过校验。已经应用的独立组不能因重试重复执行。

只有用户意思确实不清楚时才向用户澄清。模型输出格式错误不转化成用户问题；内部重试仍失败时保留受影响状态，说明该部分更新未成功，不声称已经应用，也不让用户解释技术格式。

### 执行流程

用户表达 → 确认所属任务与展示指代 → 判断表达作用 → 提出完整更新集合及来源依赖 → 检查范围、条件与冲突 → 按依赖关系分组，应用明确变化并暂缓歧义部分 → 记录版本和历史 → 检查衍生推断、候选与结论有效性 → 决定重排、重搜、补查或澄清。

### 暂缓范围

用户明确要求暂不处理“工具结果晚返回，覆盖已经更新的状态”问题。本阶段不设计或实现异步工具结果的版本校验、过期结果隔离与跨任务回传处理，也不把这些列为当前验收要求。

上面的需求版本仍用于比较结论的有效性检查，不代表已经实现工具并发控制。

## 后续动作选择

追问、查看证据、继续搜索与停止的五项基础原则及七项补充原则已确认并单独记录在 [动作选择设计备忘](action-selection-design-notes.md)。其中区分本轮停止原因与用户是否已选定商品，并补充问题优先级、整体无进展检测及结论强度与证据范围的对应关系。两份备忘均为设计约定，不代表已有运行时实现。

## 后续验收场景

比较 A、B → 排除 A → 修改预算 → 查看新候选 C → 恢复 A → 最后选择 C。

检查无关需求是否保持、排除是否可撤销、恢复商品是否按新需求核验、比较结论是否失效更新，以及暂时倾向是否被误判为最终选择。

补充验收要求：

- 用户没修改的需求保持不变，未同意的条件不被放宽。
- 假设探索不污染正式需求，单商品例外不扩展为全局修改。
- 一轮多个变化完整解析；明确独立变化不被局部歧义阻塞，依赖变化成组应用，不遗漏条件关系。
- 系统淘汰与用户拒绝可以区别处理。
- 受需求变化影响的旧结论经过重新评估后才作为当前结论使用。
- 指代对应用户实际看到的展示顺序。
- 每次更新可追溯到用户表达或明确标记的系统推断。
- 跨任务不串需求，仅继承用户明确指定的条件。
- 未知与明确无偏好可区分，后者不被反复询问。
- 撤销后不会由旧上下文自动恢复同一要求。
- 推断依据失效时重新评估，有独立依据的需求仍保留。
- 取消预算澄清不会回滚此前已生效且独立的排除决定。
- “只恢复预算”恢复修改前预算，保留其他独立修改；默认整轮撤销覆盖该轮已生效修改组。
- 撤销后重新检查衍生状态，不覆盖后来取得的商品事实或无关修改。
- 非法更新组不写入；内部有限重试不重复应用已成功的组，不把模型格式错误当作用户歧义。

补充对话案例：从耳机切换到手机；明确“重量无所谓”后继续推荐；从通勤改为宿舍使用并检查衍生偏好；“A 删掉，预算提高一点”中先完成排除、仅澄清预算；条件性恢复 A 时不提前执行。

具体字段类型、更新协议、精确澄清条件与持久化方案仍待设计；本备忘不意味着已经完成实现。
