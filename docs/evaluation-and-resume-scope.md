# 评估范围与简历表述约定

确认日期：2026-09-08。

状态：用户已确认项目方向、简历表述约定及下述六项第一版验收方案，不代表相关功能或评估已经完成。

## 已确认方向

简历围绕三类事实组织：

1. **实现了什么**：描述实际完成的能力与实现机制。例如多品类导购、需求修改与撤销、任务切换、商品原文证据核验。示例能力是否可以写入，须逐项核实实现状态，不能因已讨论或写入设计文档就视为完成。
2. **解决了哪些可复现的问题**：以真实复现的错误和修复为依据，例如假设预算误覆盖正式预算、跨任务条件串用。保留触发输入、修复前行为、修改内容及修复后验证；尚未观察到的假设场景不能写成已解决的真实故障。
3. **通过了哪些验收**：报告实际执行的案例数量、通过情况、执行范围和仍存在的限制。设计案例、程序测试和真实模型任务执行分别计数，不混用。

只写已经实现并验证的内容。当前记录的状态设计和动作选择原则，落地并通过相应验收后才可作为已实现能力写入简历。

## 评估工作的优先级

- 优先验证功能正确性、真实问题修复和回归稳定性。
- **基础 Agent 对照不作为必做项，也不作为第一版交付门槛。** 不为凑提升指标建设基线平台或增加实验。
- 若未来出现明确的设计验证需求，可以再决定是否做针对性比较；不能把此前建议的轻量对照自动列入待办或必验要求。
- 第一版确定以约 **40～60 个完整任务案例**为规模目标。此前的 240 个、约 100 个案例建议不再作为第一版规模要求；规划数量不得表述为已完成数量。

已有历史对照代码和报告保留其原本的范围与口径，本约定不要求删除它们，也不代表它们已经验证了重构后的新 Agent。

## 已确认的六项第一版验收方案

### 1. 明确已实现能力与验收范围

列出核心能力与案例的对应关系，区分已实现、未实现、未运行和运行失败。核心已实现能力须有验收案例，不要求所有讨论过的设计都在第一版落地。不能通过把已实现但失败的能力移出范围来美化结果。

### 2. 明确任务通过条件

逐案例说明完成、未完成和关键错误的判定依据，不建设通用加权总分。分别记录任务结果与过程关键错误，完整通过要求任务完成且没有关键错误。

明确约束违反、错误修改正式需求、无依据的决定性断言等不能被语言流畅或低调用成本抵消。条件性备选与正式主推荐分别判定；可完成任务不能靠一直追问或一律声称证据不足获得通过。允许多个符合要求的答案，不强制唯一商品或逐字回答。

### 3. 固定测试用户行为，被测 Agent 自主决策

测试中的用户一方采用固定输入序列或简单分支回复：

- 固定输入序列用于修改、撤销、假设探索和任务切换；每轮等待 Agent 本轮结束再发送下一条用户消息。
- 简单分支回复用于追问：问预算回答预算，问用途回答用途，不机械播放无关答案。一次询问多个维度时按已配置规则提供对应信息。
- 分支未覆盖的问题记录为测试脚本需要检查，不擅自编造答案，也不直接判 Agent 错。
- 涉及“第二个”等指代时，绑定本次实际展示顺序，不能硬编码为另一次运行的商品。

固定的是测试用户输入、商品快照和检查条件；被测 Agent 自行决定是否追问、调用什么工具、查看哪些商品以及何时回答。不得将预设工具执行路径包装成模型自主决策。

重跑从干净任务状态开始，保存模型与运行配置、商品版本和判分规则。回答文本可以不同，行为要求不变。第一版不引入自由对话的 LLM 用户模拟器。

### 4. 标准答案独立，按可判定程度选择检查方式

依据冻结商品资料标注可接受结果、相关证据、未知信息、预期状态变化及允许停止原因。评估答案独立保存，不提供给运行中的 Agent，不允许其读取评估标注判断商品资格。

预算、商品 ID、确定的状态变化等由程序检查；解释准确性、追问是否合理等语义内容，采用明确规则人工核验。保留评分依据和对应轨迹，不要求所有语义判断都自动化，不建设通用模型裁判。

隐藏用户信息不得提前泄露；若任务要求发现某个隐藏条件，场景应提供合理的追问线索，不能要求模型猜中任意未表达偏好。

### 5. 第一版约 40～60 个任务案例

数量指完整任务案例，不是单元测试函数数或对话轮次数。覆盖普通导购与关键失败边界，包括需求修改/撤销/假设、多任务切换、证据不足及动作选择。

保留少量未参与调试的案例；近似模板应归入同一侧，避免改写泄露。具体数量与分配在编制任务清单时确定，不把此前建议的 70/30 等比例视为本版要求。

不追求几百个近似模板，也不用这个规模宣称各品类具有精确的成功率。

### 6. 如实验收、保存修复证据与运行轨迹

核心问题回归案例在发布验收时应全部通过；未通过的修复不能宣称已稳定解决。完整任务集报告实际通过情况、关键错误和限制，未运行项单列，不只挑选成功记录。

对部分复杂任务重复运行，观察稳定性并报告每次结果；不要求开发阶段每次全套重复执行，也不通过反复尝试只保留成功结果。

记录任务完成情况、关键错误，以及调用次数/耗时等执行成本，成功和失败任务可分别查看。结构化日志应足以还原输入、工具结果、关键状态变化和停止原因，无须先建设全功能 trace 看板。

准备 **3 个真实、可复现问题的修复记录**，包含触发输入、修复前错误、原因、修复机制、修复后验收及仍存在的限制。预算污染、跨任务串用、无证据推荐只是候选示例，以实际发现的问题为准，不为凑故事编造故障。

第一版交付目标是核心能力范围清楚、40～60 个任务案例、明确判分规则、真实问题修复证据及可重跑日志。正式用户研究、满意度/购买转化统计、基础 Agent 对照均不是此版必做项。

## 结果表述的证据边界

没有比较依据时，不写“显著提升”“提高成功率”“减少错误率”等改善效果主张。单独测最终版本可以说明验收表现，不能证明相对其他方案的提升。

可以采用以下结构，具体内容必须来自实际证据：

> 实现某项能力；针对可复现的某类问题，采用相应机制处理；在明确范围的验收中取得实际结果，并说明限制。

已执行的测试通过，不自动证明真实用户满意度、购买转化或全部多轮任务成功。脚本化执行也不能表述为真实模型自主执行。

可复现问题的修复前后记录足以支撑对应问题的技术解释，不要求额外汇总成对基础 Agent 的普遍提升指标。
